 SOFTWARE REQUIREMENTS SPECIFICATION (SRS) WorkSphere – Project &amp; Team Management Platform Document Type: Client-Based Software Development Assignment Project Category: Full-Stack Web Application (SaaS) Difficulty Level: Intermediate Target Developer: MERN Stack Developer / Software Engineering Internee Technology Stack: React.js, Node.js, Express.js, MongoDB, Mongoose, Tailwind CSS Project Version: 1.0 Suggested Duration: 5–6 Weeks Document Status: Development Requirements 1. PROJECT INTRODUCTION 1.1 Client Background Our client is a growing software development and digital services company. The company currently manages its internal projects, employees, assignments, deadlines, and communications through spreadsheets, messaging applications, and manual reporting. As the company grows, management is experiencing difficulties keeping track of project progress, employee workloads, deadlines, and task responsibilities. The client wants to develop a centralized web-based Project &amp; Team Management Platform called WorkSphere . The platform should allow organizations to manage multiple workspaces, projects, teams, tasks, deadlines, and project activities from a single dashboard. The system must be user-friendly, secure, responsive, and scalable enough to support multiple organizations. 1.2 Business Problem The client currently faces the following problems: Project managers cannot easily track all ongoing projects. Employees sometimes forget their assigned tasks and deadlines. Management has no centralized view of employee workload. Task updates are communicated through different messaging applications. There is no proper history of who changed a task or project. Management manually prepares project progress reports. Employees cannot easily identify their pending, overdue, and completed tasks. There is no centralized notification system for assignments and deadlines. 1.3 Proposed Solution Develop a centralized platform that provides: Organization/workspace management. Team member management. Project creation and management. Task assignment and tracking. Kanban-based task management. Comments and discussions. Notifications and reminders. Activity history. Project analytics and reports. Role-based access control. The platform must synchronize all information with the backend and MongoDB database. Important: This is not a static dashboard project. All business operations must work through actual APIs and database records. 2. PROJECT OBJECTIVES The main objectives are: Provide centralized project management. Allow managers to assign work to employees. Track tasks from creation to completion. Monitor project deadlines and progress. Improve communication between team members. Provide real-time visibility into project activities. Reduce manual reporting. Provide role-based access to sensitive operations. Maintain a complete history of important changes. Support multiple workspaces with isolated data. 3. TECHNOLOGY REQUIREMENTS The developer must use the following technology stack. USER ROLES &amp; PERMISSIONS The system must support three primary workspace roles. 4.1 Workspace Owner The workspace owner is responsible for the entire workspace. Permissions: Create and manage workspace. Update workspace details. Delete or archive workspace. Invite members. Remove members. Assign roles. Create and manage all projects. View all tasks. Manage project managers. Access reports and analytics. View activity logs. Manage workspace settings. Business restriction: The workspace must always have at least one owner. The last owner cannot remove themselves or transfer ownership without assigning another owner. 4.2 Project Manager The project manager manages assigned projects and their teams. Permissions: Create projects within authorized workspaces. Update assigned projects. Add project members. Assign tasks. Update task status. Change task priority. Set deadlines. Review completed tasks. Add comments. View project reports. View project activity history. Restrictions: Cannot delete the workspace. Cannot manage workspace ownership. Cannot change workspace-level roles unless explicitly authorized. Cannot access projects outside their permissions. 4.3 Team Member Team members are responsible for completing assigned work. Permissions: View their assigned projects. View assigned tasks. Update permitted task statuses. Add comments. Upload permitted attachments. View task deadlines. Receive notifications. View their personal task statistics. Restrictions: Cannot create or delete workspaces. Cannot manage workspace members. Cannot delete projects. Cannot change project ownership. Cannot modify tasks assigned to other members unless explicitly permitted. 4.4 Permission Matrix Feature Owner Manager Member Workspace management Full No No Invite members Yes No No Assign workspace roles Yes No No Create projects Yes Yes No Delete projects Yes Authorized projects No Assign tasks Yes Yes No View assigned tasks Yes Yes Yes Update task status Yes Yes Assigned tasks Add comments Yes Yes Yes View analytics All Assigned projects Personal View activity logs All Assigned projects Relevant activities All permissions must be validated on the backend. COMPLETE APPLICATION MODULES MODULE 01 – Authentication &amp; Account Management 5.1 Client Requirement The client wants employees and managers to securely access the platform using their registered accounts. Users must not access private workspace information without authentication and proper authorization. 5.2 Required Screens Login. Registration. Forgot Password. Reset Password. User Profile. Change Password. 5.3 Functional Requirements FR-AUTH-001: User Registration The system must allow new users to register. Required fields: Full Name. Email Address. Password. Confirm Password. Validation: All required fields must be completed. Email must be valid. Email must be unique. Password must meet the defined password policy. Password and confirmation must match. Expected behavior: After successful registration, the user receives an account confirmation email or an appropriate account verification workflow. FR-AUTH-002: User Login Users must log in using email and password. Expected behavior: User enters credentials. Frontend sends login request. Backend validates credentials. Backend issues an authenticated session using JWT. User is redirected to their dashboard. Invalid credentials must produce an appropriate error message. FR-AUTH-003: Forgot Password Users can request a password reset. Expected behavior: User enters registered email. System generates a secure, time-limited reset token. System sends a reset link. User opens the link. User enters a new password. Backend validates the token. Password is updated securely. Reset token is invalidated. FR-AUTH-004: Profile Management Users can: View profile. Update full name. Update profile picture. Update phone number. Change password. View account creation date. FR-AUTH-005: Logout Users must be able to log out securely. The authentication mechanism must prevent continued use of revoked or expired sessions. MODULE 02 – Workspace Management 6.1 Client Requirement The client operates multiple departments and teams. Each department may have separate projects and employees. The client wants workspaces to separate organizational data. Example: Software Development. Marketing. Human Resources. Sales Department. 6.2 Functional Requirements FR-WS-001: Create Workspace Workspace owners can create workspaces. Fields: Workspace Name. Workspace Description. Workspace Logo. Workspace Status. FR-WS-002: View Workspaces Users can view all workspaces they are authorized to access. Display: Workspace name. Owner. Total members. Total projects. Active projects. Creation date. FR-WS-003: Update Workspace Owners can update workspace information. FR-WS-004: Delete Workspace Owners can delete a workspace after confirmation. Important business rule: Deleting a workspace must not silently destroy records. Implement an appropriate archive/soft-delete strategy and define how historical records are retained. FR-WS-005: Workspace Switching If a user belongs to multiple workspaces, they must be able to switch between them. The dashboard must update according to the selected workspace. MODULE 03 – Team &amp; Member Management 7.1 Client Requirement The client wants to invite employees and assign responsibilities according to their roles. 7.2 Functional Requirements FR-MEM-001: Invite Members Owners can invite employees using their email addresses. Invitation fields: Email. Assigned Role. Optional Message. Expected workflow: Owner enters employee email. Owner selects a role. Backend checks whether the user is already a workspace member. System creates an invitation. Invitation email is sent. Recipient accepts the invitation. Membership becomes active. Invitation statuses: Pending. Accepted. Expired. Revoked. FR-MEM-002: Member Listing Display: Employee Name. Email. Profile Picture. Workspace Role. Joined Date. Membership Status. FR-MEM-003: Update Member Role Owners can change an employee's workspace role. FR-MEM-004: Remove Member Owners can remove members from the workspace. Business rules: The last workspace owner cannot be removed. Removing a member must not erase historical activities. Their assigned tasks must remain available to authorized managers. The system should identify tasks that need reassignment. FR-MEM-005: Member Search &amp; Filters Allow filtering by: Name. Email. Role. Membership Status. The developer must understand these scenarios before implementation. The purpose is to evaluate problem-solving and business logic, not just coding ability. Scenario 01 – New Employee Joins the Company Client says: "We have hired a new frontend developer. Please add them to our development workspace and give them access to the website development project." Expected system behavior: Workspace owner opens member management. Owner enters the employee's email. Owner sends an invitation. Employee receives an invitation email. Employee accepts the invitation. Employee becomes a workspace member. Owner or authorized manager adds the employee to the project. Employee can now view authorized project information. Developer must consider: What happens if the email is already registered? What happens if the employee is already a workspace member? What happens if the invitation expires? Can the employee access the workspace before accepting? What happens if the owner revokes the invitation? Scenario 02 – Manager Assigns a Task Client says: "Assign the homepage development task to Ahmed. The deadline is November 15, and the priority is High." Expected behavior: Manager opens the project. Manager creates a task. Manager selects Ahmed. Manager selects priority and deadline. System validates the project membership. Task is saved. Ahmed receives a notification. Task appears in Ahmed's My Tasks page. Developer must consider: What if Ahmed is not a project member? What if the deadline is before the start date? What if the project is archived? What if the manager does not have permission? Scenario 03 – Employee Updates Task Status Client says: "The developer has started working on the homepage. Move the task from To Do to In Progress." Expected behavior: Employee opens the Kanban board. Employee drags the task to In Progress. Frontend sends status update API request. Backend checks permission. Database updates the status. Activity log is created. Relevant users receive notifications. Developer must consider: What if the API request fails? What if the task is updated by another user simultaneously? What if the employee attempts to update another employee's task? What if the task is already completed? Scenario 04 – Task Deadline Changes Client says: "The API integration is taking longer than expected. Change the deadline from November 15 to November 18." Expected behavior: Manager opens task details. Manager updates the due date. System stores the new deadline. Activity history records old and new dates. Assigned employees receive notifications. Previous scheduled reminders are recalculated. Scenario 05 – Employee Misses a Deadline Client says: "The payment integration task was due yesterday, but it is still incomplete. Highlight it as overdue." Expected behavior: Backend identifies the expired due date. Task appears in the overdue list. Dashboard overdue count increases. Manager can filter overdue tasks. Assigned employee receives an appropriate reminder. Important: Do not automatically change the task's workflow status to Overdue. Overdue should be calculated from the due date and completion status, independently of the workflow status. Scenario 06 – Manager Completes Project Review Client says: "The development team says the website is complete. I want to review all completed work before closing the project." Expected behavior: Manager opens project. Manager views tasks in In Review. Manager reviews task details. Manager approves or requests changes. Approved tasks move to Completed. Project progress recalculates. Project can be marked Completed only when its completion requirements are satisfied. Scenario 07 – Employee Leaves the Company Client says: "One of our developers has left the company. Remove their workspace access but keep all historical records." Expected behavior: Owner opens member management. Owner removes the employee. Employee loses workspace access. Existing task records remain. Existing comments remain. Activity history remains. Uncompleted tasks are flagged for reassignment. The owner can reassign those tasks. Scenario 08 – Project Manager Wants a Monthly Report Client says: "Generate a report for November showing how many tasks were completed, how many are overdue, and which employees have the most pending tasks." Expected behavior: Manager opens reports. Selects November date range. Selects the relevant project or workspace. System retrieves matching data. Dashboard displays statistics. Manager exports the report to CSV. The report must use database queries, not frontend calculations based on incomplete page data. Scenario 09 – User Belongs to Multiple Workspaces Client says: "I work with both the development and marketing teams. I want to switch between them without logging out." Expected behavior: User opens workspace selector. System displays authorized workspaces. User selects another workspace. Application loads the selected workspace. Dashboard, projects, and member information update accordingly. Data from one workspace must never leak into another. Scenario 10 – Concurrent Task Updates Client says: "Two managers are updating the same task at the same time. We don't want one person's changes to silently overwrite the other person's changes." Expected behavior: Both users open the same task. First user updates the task. Second user submits an update based on an older version. Backend detects the version conflict. System rejects the stale update or safely reconciles non-conflicting changes. User receives an informative message and can refresh. The developer should consider Mongoose optimistic concurrency or a version-based update strategy. Scenario 11 – Unauthorized Access Client says: "A normal team member should not be able to delete a project by manually calling the API." Expected behavior: User attempts a restricted action. Backend checks authentication. Backend checks workspace membership. Backend checks role and resource-level permission. Request is rejected. Appropriate HTTP status is returned. Frontend restrictions alone are not acceptable. Scenario 12 – Duplicate Invitation Client says: "I accidentally sent the same employee an invitation three times. The system should not create duplicate invitations." Expected behavior: Check existing pending invitations. Prevent duplicate active invitations. Allow authorized resend. Generate a fresh secure token when appropriate. Expire or revoke previous tokens. Record invitation history. 7.
